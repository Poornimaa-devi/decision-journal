# Day 47 — Authentication Middleware

## Purpose
Checks incoming requests for a valid JWT before allowing them to reach 
protected controllers. Attaches identified user info to req.user for 
downstream use.

## Flow
1. Read Authorization header
2. Check it exists and starts with "Bearer "
3. Extract token, verify with jwt.verify()
4. Valid → req.user = decoded payload → next()
5. Invalid/missing → respond 401, request never reaches controller

## Why try/catch, not .then()/.catch()
jwt.verify() is synchronous — it returns immediately or throws immediately, 
unlike Mongoose calls or bcrypt, which are asynchronous (Promise-based).

## Why not use next(err) on failure
An invalid/missing token is an expected, normal case (not a server error), 
so it's handled directly with a 401 response rather than routed to 
errorHandler.js (meant for unexpected failures).

## Important rule
Signup and login routes must NOT use this middleware — users don't have 
a token yet at that point.

## How it fits into Decision Journal
This middleware will sit in front of goal/progress routes (and any future 
protected routes) starting Day 48-49, ensuring only logged-in users can 
access their own data.
