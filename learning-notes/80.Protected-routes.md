# Day 80 — Protected Routes & Login

## Frontend route protection = UX, not security
Redirecting logged-out users avoids broken pages. The real protection is the
backend authMiddleware, since anyone can bypass the UI.

## Token storage
Token saved in localStorage via tokenStorage.js (single place to change).
Trade-off: readable by any JS on the page (XSS risk). httpOnly cookies set
by the server are safer but more complex.

## Context API
createContext() + Provider + useContext(), wrapped in a useAuth() hook.
Shares auth state (token, isAuthenticated, login, signup, logout) with any
component without prop drilling.

## apiFetch changes
- Token read from storage on every request
- auth: false for public endpoints (login/signup)
- On 401: clear token, dispatch "auth:expired" → provider clears state →
  ProtectedRoute redirects to /login
- Errors now use the server's message

## Route structure
Layout routes (no path) wrap children: ProtectedRoute (access control,
renders <Outlet />) → Layout (Header + Navbar + <Outlet />) → pages.
/login and /signup sit outside the protected group.

## Gotchas
- Hooks must run before any early return
- Remove every TEMP_TOKEN import after deleting the constant
- Use incognito windows to test two users (separate localStorage)

## How it fits into Decision Journal
Users sign up, log in and out themselves; the app no longer depends on a
token pasted from Postman, and two users can be tested in the browser.
