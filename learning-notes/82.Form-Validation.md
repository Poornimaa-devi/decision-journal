# Day 82 — Form Validation

## Two layers
Frontend validation = fast, friendly feedback (can be bypassed).
Backend validation = the real rules (schema + middleware).
Server messages must reach the UI too.

## When to show errors
On blur (leaving a field), live on change once a field has an error, and all
at once on submit. Never on first render.

## useForm hook
Tracks values, errors, touched, submitError, isSubmitting. One handleChange
works for every field via e.target.name (computed key: [name]: value).
Success resets; failures put server field errors under the right inputs.

## Reusable pieces
validators.js (one validator per form, returns { field: message }),
FormField (label + input/textarea/select + error with aria-invalid and
aria-describedby), noValidate on <form> to use our messages.

## Backend errorHandler improvements
ValidationError → 400 { message, errors: { field: message } }
CastError → 400, duplicate key (11000) → 409, bad JSON → 400.
Previously these were all 500.

## apiFetch
Throws errors carrying status and fieldErrors from the response body.

## Who shows an action's error?
Whoever owns the UI that triggered it: forms show their own submit errors;
pages show errors for buttons (toggle/delete).

## Gotchas
Missing name attributes, hooks after an early return, "" for optional
ObjectIds, validators and schema drifting apart.

## How it fits into Decision Journal
All four forms give clear, consistent, accessible feedback, and the server's
validation messages appear next to the fields they belong to.
