# Day 70 — Reflections

## The problem: a parent that varies by type
Unlike Progress/Milestone (always point to Goal), a Reflection can be about 
EITHER a Goal or a Decision.

## Solution: two optional references + a type label
targetType: enum ["Goal", "Decision"]
goal: ObjectId ref "Goal", default null
decision: ObjectId ref "Decision", default null
Only one of goal/decision should be filled, matching targetType.

## Validation that belongs in the CONTROLLER, not the schema
"Exactly one of goal/decision must be set, based on targetType" is a 
relationship BETWEEN fields — this kind of business logic often belongs 
in the controller, not the schema, unlike simple single-field rules 
(required, enum, min/max) which belong in the schema itself.

## Populating multiple optional references
.populate("goal", "title").populate("decision", "title") — chainable; 
whichever field is actually set gets resolved, the other stays null.

## How it fits into Decision Journal
Users can now write reflective journal entries tied to either a specific 
decision or a specific goal — completing the full core entity set Phase 
10 set out to build (Decision, Goal, Progress, Milestone, Reflection).
